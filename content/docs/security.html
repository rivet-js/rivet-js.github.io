Security

Data stays data.
Raw HTML stays explicit.

Rivet keeps ordinary interpolation separate from trusted HTML parsing so the security boundary is visible in source.

Safe interpolation

Interpolated strings in template content become text nodes; interpolated attributes are assigned as attribute values. They are not reparsed as template markup.

const name = state('<img src=x onerror=alert(1)>');
html`<p>${name}</p>`; // text, not an image

Rivet rejects .innerHTML, .outerHTML, and .srcdoc property bindings because they turn strings back into parser input.

Trusted HTML sinks

The static markup written inside html`...` is developer-authored application source and is trusted. Hypermedia swap() also deliberately parses HTML, so server-returned swap content must be treated as trusted application output. Rivet does not pretend to be an HTML sanitizer.

Requests and URLs

request() keeps native fetch semantics. Rivet does not replace server authorization, CSRF protection, CORS policy, URL validation, or redirect policy. Declarative r-get/r-post map onto the same request engine.

CSP-friendly events

Dynamic event handlers use addEventListener rather than generated inline JavaScript. Applications can therefore use a restrictive Content Security Policy without Rivet requiring unsafe-eval.
